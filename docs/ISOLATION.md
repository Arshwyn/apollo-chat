# Isolation model

Two people use the app. Neither may see the other's chats, photos, transcripts or health connectors. This page says who can see what and what enforces it.

## Who can see what

| Data                                        | Owner can                                 | Other user can                                            | Enforced by                                                                                                                                                                                                                                                                                            |
| ------------------------------------------- | ----------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Chat history (`users/<user>/chat.db`)       | read, rename, delete                      | nothing; their id returns 404                             | separate files per user, the store opens only the verified user's path, every route is scoped                                                                                                                                                                                                          |
| Staged and run photos (`users/<user>/tmp/`) | upload, send, remove an unsent one        | nothing; their photo id is rejected                       | per-user directories, ids are random and checked against the caller's tree, links are never followed; HEIC uploads are decoded in memory and only the sanitised JPEG is ever written (no HEIC bytes on disk); removed at once when discarded, swept after about 1 h unsent and 24 h after a failed run |
| Transcripts (`users/<user>/transcripts/`)   | nothing directly; the agent may grep them | nothing                                                   | per-user directories, the host hook allows only the active user's folder                                                                                                                                                                                                                               |
| Agent memory (other than day files)         | nothing directly                          | nothing                                                   | the host hook (per process, from `APOLLO_USER`)                                                                                                                                                                                                                                                        |
| Day files (`history/YYYY/MM/DD/*.md`)       | read, through the Daily logs screen only  | nothing; their dates and names are not listed or readable | the gateway: strict validation of user, date and name, a user-scoped root, `realpath` plus `lstat` confinement (no link followed at any level), regular `.md` files only, a size cap, read-only code path                                                                                              |
| Health connectors                           | through the agent                         | not through their run                                     | gateway tool lists plus the host hook                                                                                                                                                                                                                                                                  |

## Layers

1. **Identity.** Only a valid Cloudflare Access token for a mapped email gets in. The user comes from the verified token and nowhere else (no parameter, header or body field is read for it).
2. **App.** Per-user database files, per-user directories, ids validated against strict patterns, `404` for anything that is not the caller's.
3. **Gateway.** Accepts only `{user, prompt, run_id, photo_paths, check_dayfile}`; the user must be a configured id; at most 16 photo paths, each of which must resolve (symlinks followed) into that user's run directory; the gateway alone builds the argv, working directory and environment, and sets `APOLLO_USER`, `APOLLO_CHAT_RUN=1` and `APOLLO_CHAT_DATA`. Tool allow and deny lists are computed per user from `GATEWAY_USERS`; chat runs get no shell. The gateway trusts the app container for the `user` field of a run request: one user per request, and the container is inside the trust boundary (it is the only client of the socket). Separation after that point does not rely on the app: it is enforced by the gateway's per-user environment and connector map and by the host hook. The gateway also answers two read-only requests, `dayfiles_list` and `dayfile_read` (fields `op`, `user`, and `limit`/`before` or `date`/`name`; nothing else is accepted). Every field is checked by one shared validator (the user must be configured, the date a real calendar date, the name `^[a-z0-9][a-z0-9_-]{0,63}\.md$`), paths are built only from those validated parts under `<APOLLO_MEMORY_ROOT>/<user>/history`, the user's folder is re-resolved on every request and must be a real directory inside the real memory root, and each level plus the file must be a real directory or regular file (a link is refused even if it resolves inside). Reads are capped at 256 KiB and must be UTF-8; listings are newest first and bounded (30 days by default, 100 at most). Errors are the generic codes `invalid`, `not_found`, `too_large` and `unavailable`, and the log line holds only the time, operation, user and code, never dates, names, paths or content. As with runs, the gateway trusts the app for `user`; the app derives it from the verified session only. The code path uses only directory reads, `lstat` and read-only opens (a test checks the module for write APIs).
4. **Host hook.** Reads the user, data directory and run id from per-process variables, fails closed on missing or invalid values, on a conflict with the lock and on malformed hook input, and applies a default-deny allowlist to every tool call in the run (not only a call tagged as the agent). File tools are allowed only on canonical paths inside the user's own memory folder, transcripts folder or this run's photo folder, plus read-only access to three named shared start-up files (persona, rules, index) matched by exact canonical path; connectors only the user's own. Glob patterns and Grep filters are only filters under that confined path (relative, no `..`, no braces or brackets; a leading `**` is allowed). Mailbox access is denied in chat runs. See [`HOOK.md`](HOOK.md).
5. **Tests.** `test/isolation.test.js` and `test/api.test.js` (API and storage), `test/gateway.test.js` and `test/dayfiles.test.js` (gateway, including the day-file validator, confinement, size cap and read-only checks with two users), `test/gatewayClient.test.js` and `test/dayfileRoutes.test.js` (client and endpoints), `test/hook/hook.test.js` (the hook, with both users running in parallel).

## Residual risk (be honest about it)

- Chat runs have no shell: the tool surface is the file tools, web lookups and the user's connectors, and the hook confines the file tools by canonical path. All runs still share one OS user, so the hook is defence in depth; the stronger boundary would be separate OS users or containers.
- **Prompt injection.** Screenshots are untrusted input and could carry instructions. The tool allowlist, the connector denylist and the hook limit what an injected instruction could do; they do not make it harmless.
- A process that can reach the gateway socket can ask for a run for either user. The socket is group-restricted (0660 in a 0750 directory) and should stay reachable only by the app container and the service user.
- Day files are plain text on the host, readable by the service user and by backups of the memory folder; the Daily logs screen adds a read path to them for their owner, guarded as above. The gateway trusts the app for `user` on this path too, so a compromised app container could ask for either user's day files; that matches the trust placed in it for runs.
- Logs and the database never hold photos, but chat text is stored in plain SQLite files readable by the service user and by backups of `DATA_DIR`.
